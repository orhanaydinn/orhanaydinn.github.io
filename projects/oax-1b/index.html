Custom 1B LLM for Robot Tool Calling

OAX-1B-Humanoid is a custom LLaMA-style language model developed as the high-level reasoning layer of a humanoid robot assistant. It translates natural-language requests into structured JSON actions that can be checked before execution.

Problem

Natural language is flexible; robot interfaces must be predictable

A general language model can produce useful instructions, but physical robot software requires outputs that are structured, machine-readable, and easy to validate. The central problem was therefore not only language generation, but reliable translation from user intent into a constrained robot-assistant action schema.

The model was designed to propose high-level actions rather than directly control motors, servos, or joint trajectories. This keeps language understanding separate from deterministic safety and execution logic.

Training Strategy

Base pre-training followed by supervised tool-calling adaptation

01

Base model pre-training

A custom 1B-parameter LLaMA-style model was trained as a general base language model before robot-specific adaptation.

02

Robot-assistant dataset

Training examples paired user requests with strict JSON outputs covering chat, clarification, refusal, and tool calls.

03

Supervised fine-tuning

A LoRA adapter was trained to specialise the base model for structured robot tool-calling behaviour.

04

Inference integration

The base model and adapter are loaded together and used behind an external validation layer in the humanoid robot pipeline.

Output Contract

A fixed four-field JSON schema

Required response schemaJSON
{
  "type": "tool_call",
  "response": "short natural-language explanation",
  "tool": "tool_name",
  "arguments": {}
}

chat — a normal response without tool execution.

tool_call — a request to invoke a supported robot tool.

clarify — asks for missing or ambiguous information.

refuse — rejects unsupported or unsafe requests.

Supported Actions

A deliberately compact tool vocabulary

The fine-tuning data focuses on six high-level robot-assistant actions:

get_visible_objects get_robot_status search_object pick_object place_object stop

Keeping the action set compact reduces ambiguity and makes downstream validation easier. New tools can be added later by extending the training data, schema rules, and controller logic together.

Prompt Format

Role tags define the model interaction

Training and inference promptTEXT
<|system|>
You are OAX, a humanoid robot assistant.
Always return valid JSON with exactly:
type, response, tool, arguments.

<|user|>
Find the cup.

<|assistant|>
{"type":"tool_call","response":"Searching for the cup.","tool":"search_object","arguments":{"object":"cup"}}

During inference, the prompt ends with <|assistant|> so the model generates the next structured response.

Model Packaging

Base weights and LoRA adapter remain separate

The repository stores the pre-trained base model and the supervised fine-tuning adapter in separate folders:

base_model/
lora_adapter/

This structure preserves the original base model while allowing the robot-specific behaviour to remain modular, lightweight, and replaceable.

Safety Architecture

Model output never directly changes robot state

User Command→LLM JSON→JSON Parsing→Planner / Controller→Repair or Reject→Tool Execution

The model acts as a high-level reasoning component. Deterministic software checks the tool name, arguments, current state, and action validity before execution.

Limitations

Experimental model behaviour still requires external control

Premature tool calls

The model may occasionally request an action before all required state information is available.

Argument inconsistency

Object or destination names may need normalisation or repair before execution.

No direct low-level control

The model is not suitable for direct motor, servo, trajectory, or safety-critical control.
